# BioSample screenshot interpretation

The user supplied a screenshot of a BioSample input table and a field-description list, not a complete downloadable Excel template. Visible fields: `Sample name`, `NCBI taxonomy id`, `Organism`, `Age`, `Biomaterial provider` (marked M*), followed by optional `Cell line`, `Cell subtype`, `Cell type`, `Specimen voucher`, `Tissue`, `Sex`, `Developmental stage`, `Disease`, `Isolate`, `Geographic location`, `Collection Date`, and `Culture collection` in the shown portions. M* and O are screenshot labels; inspect the current downloaded template for authoritative requiredness and accepted missing-value terms. The second screenshot describes KRA file-name equality and `.gz` upload conventions, not project attributes.

The example clinical workbook has `SAMPLE`, `mRNA`, `QC_Macrogen`, `AGE`, `SEX` among 73 columns and 91 data rows. For the observed version, 89 rows show QC `True` with an mRNA ID and 2 show `FAIL` with `mRNA=-`. Do not strip `(QC fail)` from a `SAMPLE` string to invent a BioSample ID. The supported initial mapping is mRNA -> Sample name for QC-passing samples, AGE -> Age only if the researcher confirms its unit, and M/F -> male/female if the template permits these values. A human project may suggest a taxonomy but does not prove the analyzed biological specimen, nor the material provider, sample tissue, collection date, or accession relationship. Require independent documented facts.

Keep project-level description, study design, taxonomy scope, and BioProject ID in a separate project mapping. Do not populate project attributes by copying a single patient row. Keep KRA run/file metadata separate from BioSample as it needs actual read files and sequencing methods.
